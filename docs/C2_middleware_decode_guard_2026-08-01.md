# C2 — malformed percent-escapes at the router boundary (Hub, WSL)

**Box:** `ghost@Ghost` (WSL Hub), repo `/home/ghost/projects/trevor-dashboard`, branch `master`.
**Date:** 2026-08-01. **Money path:** no. **DB writes:** none (read-only replica throughout).

Closes the second, distinct defect B4 isolated and carried as open.

---

## The defect

`%2`, `%zz`, `%%` and `%C3%28` returned **HTTP 500 on every dynamic route**.

These are *structurally invalid* escapes, not valid escapes that decode to `%`
(B4 closed that class at the handler with `api-helpers.safeDecodeSegment`).
**Next's own router throws while decoding the segment, before any handler code
exists to guard.**

Reproduced before the fix:

| Request | Before |
|---|---|
| `GET /api/health/digests/%2` | 500 |
| `GET /api/health/digests/%zz` | 500 |
| `GET /api/health/digests/%%` | 500 |
| `GET /api/health/digests/%C3%28` | 500 |
| `GET /api/memory/brain/%2` (zero `decodeURIComponent` calls) | 500 |
| `GET /api/no-such-route-%2` | 404 |
| `GET /no-such-page-%2` · `/memory/%2` | 404 |

## 🚨 B4's verdict was inherited but NOT taken on trust

B4 concluded *"closing it means `middleware.ts`."* That was the most load-bearing
inherited claim in this prompt, so it was re-derived here by a test B4 did not run.

**Middleware runs to completion on the malformed path, upstream of the throw:**

```
no-cookie GET /api/health/digests/%2  -> 401   (not 500)
no-cookie GET /api/memory/brain/%2    -> 401
```

A 401 there is generated by `middleware.ts` itself. Because middleware returned a
response, routing never happened and the throw never fired — the guard behaviour
was already demonstrable by accident.

**And `nextUrl.pathname` still carries the RAW escapes at that point**, proven
against two pieces of existing exact-match logic:

```
GET /%64ashboard        -> 307   ( %64='d'; did NOT match the /dashboard legacy key )
GET /dashboard          -> 308   ( positive control )
no-cookie GET /%6Cogin  -> 307   ( %6C='l'; did NOT hit the /login allowlist )
no-cookie GET /login    -> 200   ( positive control )
```

A decoded pathname would have matched both. **This is a real bug with a reachable
fix, not a framework limitation.**

## The guard

`middleware.hasMalformedEscape` — the detector is **B4's own predicate**, not a
second style: "malformed" means exactly what `safeDecodeSegment` means by it,
*`decodeURIComponent` throws*. Only the disposition differs — B4 passes the value
through so a handler can reject it; here there is no handler to reach, so we
reject.

Deliberately **not a regex**: an RFC-3986 pattern would be a second definition of
malformed, free to drift from what the router actually chokes on.

⚠️ **It cannot literally import `safeDecodeSegment`.** `api-helpers.ts` imports
`child_process` and `path` at module top level and middleware runs in the Edge
runtime. Do not "DRY this up" — the shared thing is the predicate, and it is one
line.

### Three narrowings, each measured — because middleware is a global interceptor

1. **Path only, never the query.** A malformed escape in the query does **not**
   throw (`…/2026-08-01?x=%2` → 200, `/health?tab=activity&x=%zz` → 200).
   Guarding it closes zero defect and risks the login `?from=` flow.
2. **`/api/*` only.** All ten dynamic segments live under `src/app/api/`; there
   are **zero dynamic page routes**. Page paths already 404 honestly and are
   untouched.
3. **After `verifyToken`.** The guard sits downstream of the direct-IP 301, all
   seven legacy redirects, the entire allowlist (`/login`, `/api/auth`, the
   exact-match `/api/health` liveness probe, the bearer-token `/api/cost/refresh`
   worker, `/_next/*`) and both auth-failure paths. Every one is structurally
   unreachable from it.

Body is readable, not empty: `{"error":"malformed percent-escape in path"}`.

## malformed ≠ absent ≠ not-found — all three stay distinct, and observably so

- **malformed** → 400 from middleware, body `malformed percent-escape in path`.
- **absent** → untouched. An empty segment decodes fine:
  `/api/health/digests/` → 308, `/api/health/digests` → 200 (list route).
- **not-found** → untouched for any VALID escape. `%20` and `%25` decode cleanly,
  so `/api/intel/downloads/a%20b.md` still **404**s, and `%25` still returns
  B4's **handler** 400 (`invalid date (expected YYYY-MM-DD)`) — a different body
  from the middleware 400, so the two conditions are distinguishable on the wire.

### 🚨 ONE ACCEPTED BEHAVIOUR CHANGE — DO NOT "FIX" IT BACK

**`/api/no-such-route-%2` returns 400, where it used to return 404.**

Middleware cannot know whether a path resolves to a route without duplicating the
route table, and that duplication would be a far worse trade than the one it buys.
A URI carrying a syntactically invalid escape cannot be canonically resolved at
all, so 400 reports the **earlier** of two errors rather than swallowing the later
one — fixing the escape still yields a 404, so no information is lost, only
ordered correctly.

**Ghost accepted this explicitly at the C2 gate and amended the gate to match.**
It was surfaced before any code was written, not discovered afterwards. Reverting
it to chase a 404 re-opens the 500s. Recorded at the guard site as well as here.

Well-formed not-found is unaffected: `/api/no-such-route` → 404,
`/no-such-page-%2` → 404, `/memory/%2` → 404.

## 🚨 What is NOT verified here

**The browser render regression was NOT run.** B4's harness needs a WSL-side
authenticating reverse proxy (Windows Chrome cannot be given the session cookie
via CDP — it binds `--remote-debugging-port` to `127.0.0.1` on the *Windows*
side). Starting that listener was **refused by a permission control**, twice, and
was not worked around. There is no Linux-side browser on this box
(`chromium`/`google-chrome`/`puppeteer`/`playwright` all absent), so no
alternative render path exists.

**What is offered instead is a weaker, different evidence tier and is labelled as
such:** the print/render path is unchanged *by construction* — `git diff` is
**one file, +87/−0, `src/middleware.ts` only**, and all six render-path files
(`markdown-print-document.tsx`, `digest-markdown.tsx`, `digest-download-sheet.tsx`,
`download-format-sheet.tsx`, `downloads-section.tsx`, `activity-feed-section.tsx`)
are byte-identical to HEAD. Their API inputs were separately proven byte-identical
(the `sha256` above). Identical code over identical bytes cannot render differently.

**That is an argument, not a rendering.** It does not discharge the "verify by
rendering" constraint and is not claimed to. The render check remains **OPEN** and
should be run by a prompt permitted to bind the local proxy.
