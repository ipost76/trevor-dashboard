## WSL Hub Access & Keepalive

> Current-state. Load-bearing infra that went silently dead for 34 days before anyone noticed (RECON-INFRA_HEALTH-010 / HUB-BOOT-03, 2026-07-14).

- **The distro must be pinned UP or the whole Hub goes dark.** A WSL2 distro is reaped ~30s after its last *attached* `wsl.exe` client exits (`.wslconfig vmIdleTimeout=-1` keeps the shared utility VM, but NOT an individual distro). When `TrevorHub` Stops, its `tailscaled` + `sshd` + dashboard go with it — the public Funnel loses its backend (`ERR_SSL_PROTOCOL_ERROR`) and both SSH paths die. One cause, all symptoms.
- **Keepalive mechanism (Windows host, NOT in this repo):** Windows Task Scheduler task **`WSL-Keepalive`** → `C:\Users\ipost\.wsl-ssh\wsl-keepalive-launch.ps1`, a supervisor holding one blocking `wsl.exe` client per distro (apify/RhondaDev/TrevorHub/Terrence), restarting any that drops (30s loop). **Self-heals without a reboot** (B1, 2026-07-14): a **periodic 5-min TimeTrigger** relaunches a dead supervisor; `MultipleInstancesPolicy=Parallel` + a `Global\WSLKeepaliveSupervisor` mutex make “is a supervisor alive?” an OS fact (no zombie can lock out a relaunch); `RestartCount=3`; it appends to `wsl-keepalive.log`. Runs as InteractiveToken (relies on autologon). If the Hub is dark, from the Windows tab: `Start-ScheduledTask -TaskName WSL-Keepalive`.
- **Correct SSH target for the WSL tab:** **`ghost@100.113.60.59:2232`** (the distro's own tailnet IP, direct — preferred). Also works: **`ghost@100.79.103.74:2232`** via the Windows netsh portproxy, but that path depends on a **hardcoded WSL NAT IP** (`172.27.110.9` today) that drifts on every distro restart — the `WSL SSH Portproxy Refresh` task re-tracks it. **NOT `:22`** on either node (distro `:22` is closed; Windows `:22` is a *different* OpenSSH server, user `ipost`).

## 🚨 Plain-English surface: what is protected, and where the sweeps kept missing

> The Hub is the sole observation surface for the unattended paper run, so a raw column name on screen is a real defect, not cosmetics. This section is the current state of that work — the mechanism, the protected surfaces, and the two blind spots that made the same defect recur.

### The mechanism

- **`src/lib/plain-labels.ts` is the single machine-identifier → English layer.** Two contracts live in it, and the difference matters:
  - **`plain*()` — map + NEUTRAL FALLBACK, returns a string.** For ONE named field. An unmapped key reads "Other check" / "Mismatch" / "Uncategorised" — never the key.
  - **`plainMetric` / `plainAxis` / `plainGate` / `plainCheckStrict` / `plainBudgetBucket` — ALLOWLIST, returns `string | null`.** For walking an UNKNOWN key set. `null` means the caller MUST drop it and count it; the tally renders through `bitsWithDropped()` as **"+N more"**, so an allowlist's information loss is visible rather than silent. **An unmapped key is structurally unrenderable — it does not depend on a fallback string staying neutral.**
- 🚨 **Use own-property lookup on any untrusted key set.** A bare `MAP[k]` returns `Object.prototype` for `"__proto__"` and the `Object` function for `"constructor"`; neither is null, so `?? null` never fires and a non-string reaches React, which throws on an object child and blanks the panel. The allowlist helpers go through `ownLabel()`. ⚠️ **The older `plain*()` helpers still use a bare lookup and carry this latent crash** — left alone because that file is additive-only by contract, but it is real and worth a follow-up.
- **`plain-labels.ts` is APPEND-ONLY.** Never rename, remove, or change an existing fallback — other surfaces read it live. Add a new helper instead (`plainMismatchKind`, `plainCheckStrict` and `plainCheckDetail` all exist for exactly that reason). Measured additive since `9662129`: **+297 / −0**.
- **Extend a map only with keys OBSERVED in live data or DOCUMENTED by the producer** — never a guess. An allowlist entry that names a key which never appears is inert; one that guesses a real key's English name ships a wrong label. When in doubt, omit: the cost is a counted row, not a disclosure.

## Parallel safety: file locks (use these — worktrees retired 2026-06-16)

- Before editing a file: `scripts/locks/with_file_lock.sh <path> -- <edit command>` — acquire → run → release (releases even on failure/signal).
- To commit: `scripts/locks/git_commit_serialized.sh -- "git add <specific-file> && git commit -m '...'"` — **pass the whole compound command as ONE quoted string** so the `add`+`commit` run together under the global git-index lock. The unquoted `-- git add x && git commit` form would split on `&&` at your own shell and run the commit OUTSIDE the lock. One committer at a time; bare `git add .` / `-A` / `--all` is refused (even behind `git -C <dir>`).
- Locks live in `.locks/` (gitignored, native ext4 only). Stale locks auto-reclaim only when age >15min AND the owner is **definitively** dead (`kill -0` on the durable pid, on this host) — see the indeterminate-liveness rule below.
- 🚨 **THE LOCK KEY IS CANONICALISED BEFORE ENCODING — a relative path anchors at the REPO ROOT, never at `$PWD` (fixed B1, 2026-08-01).** This is the **bypass** fix, and it was the most important thing on this box: before it the key was the caller's **raw argument string**, so one file had as many locks as it had spellings. Measured here: `src/app/page.tsx`, `./src/app/page.tsx`, the absolute path, and `app/page.tsx` from `src/` produced **FOUR independent locks and THREE were acquired concurrently** — not a lying diagnostic, **no mutual exclusion at all**. Now five spellings across four cwds collide on one lock and the four contenders wait. 🚨 **The contract this establishes: a relative lock path is REPO-ROOT-relative.** `lock_acquire.sh app/page.tsx` run from `src/` locks `<repo>/app/page.tsx`, not `<repo>/src/app/page.tsx` — cwd-independent by design, because anchoring at `$(pwd)` is the same ambient-state defect wearing a different hat. Pass repo-relative or absolute paths. Symlinks are deliberately **not** resolved (normalisation is lexical), so a key cannot change under a filesystem edit.
- ✅ **A held lock can no longer be invisible to the diagnostic (found + fixed B1).** The `./`-prefixed spelling used to mint a **dot-prefixed** lock directory, and `lock_status.sh` globs `*.lock`, which does not match dotfiles — it listed 3 of 4 held locks. ## 🚨 The five concurrency hazards

**The lock serializes EDITS and does NOTHING about any of these.** Holding a lock is not protection from them.

1. **Locks released on a FAILED commit** — the failure path can drop the lock while your work is still uncommitted.
2. **A sibling's index op UN-STAGES your `git add`** — the git index is shared; your staging is not private.
3. **A guard scanning the WORKING TREE blocks on a sibling's untracked file** — their mess fails your commit.
4. **A guard scanning the SHARED INDEX** — same root cause, different surface.
5. 🚨 **Backticks in a commit message die on shell expansion and leave files STAGED.** Use **`git commit -F <file>`** — always. A half-committed staged tree is the worst outcome of the five because it looks like nothing happened.

## 🚨 The live-store test guard — and why it is written FOUR times (B11, 2026-08-02)

**`get_connection()` in all four `lib/*_db.py` modules REFUSES to resolve its own live store when the process entry point is a test.** Before B11 there was no guard at all, and `tests/test_cascade_calibration.py` wrote the live `data/trainer.db` — `PRAGMA journal_mode=WAL` plus `init_schema()`'s 7 DDL statements inside a real COMMIT — **twice on every run, with every failure eaten by `except Exception: pass`**, and nothing warned anyone.

**How it decides (`_under_test()`):** `PYTEST_CURRENT_TEST` set · `pytest` in `sys.modules` · `basename(sys.argv[0])` starts with `test_`/`pytest`. The canonical invocation here is `python3 tests/test_X.py`, so **`sys.argv[0]` IS the test file** — no runner, no CI and no `conftest.py` is needed. 🚨 **A `conftest.py` would be INERT on this box** (pytest is genuinely absent, so Python never loads one) **and would read as coverage while providing none — do not add one.**

🚨 **IT FAILS TOWARD REFUSING.** An indeterminate `argv[0]` — `-` (stdin), `-c`, or empty — counts as UNDER TEST and is refused. Measured at B11: the Hub's ~20 inline-python routes run as `argv[0] == "-"` but reach `trevor.db` through raw `sqlite3.connect` and import **none** of `lib/*_db.py`, so **live blast radius is zero today**. A future inline caller fails **loudly, naming the hatch**, never silently against the live store. A false refusal costs an error message; a false permit costs the store.

**The escape hatch, deliberately verbose:** `get_connection(allow_live_under_test=True)` or `ALLOW_LIVE_STORE_UNDER_TEST=1`. It raises `ValueError` naming the store, the resolved path, the env var to redirect, and both hatches. **Raising, never redirecting** — a silent redirect makes a test pass while measuring nothing, which is the exact class this campaign keeps finding.

🚨 **THE GUARD IS DUPLICATED 4× ON PURPOSE. DO NOT FACTOR IT INTO A SHARED `_common_db.py`.** `lib/watcher_db.py` and `lib/watcher_integrity_db.py` are guaranteed to have **ZERO cross-import in BOTH directions** so the fragile LLM review-brain physically cannot write the integrity store — and that is **AST-proven by `tests/test_watcher_independence.py` (5/5, re-run after B11)**. A shared helper would hand both modules one common import and **silently delete a structural safety property while looking like a tidy-up.** The same reasoning already duplicates `resolve_db_path` / `init_schema` / `utc_now` / the replica guard between them. **Four copies is the design, not debt**, and each copy carries the comment saying so.

⚠️ **SCOPE LIMIT — state it, don't rediscover it.** The guard lives INSIDE `get_connection()`, so it only sees callers that come through `get_connection()`. **Raw `sqlite3.connect(...)` sites bypass it entirely and are structurally invisible to it** — 125 such sites repo-wide outside the four store modules (mostly the legitimate `query_*.py` replica readers), 22 under `tests/`, all of which now target `:memory:` or a temp path. Such a site must be given an explicit path by hand; the guard cannot help it.

🚨 **THE INDIRECT ROUTE IS THE ONE THAT MATTERS, AND A TEST-SIDE FIX COULD NOT HAVE CAUGHT IT.** Two escapes reached the live store through a **production function's `conn=None` / `db_path=None` default** followed by a **function-local** `from lib.trainer_db import get_connection` — `compass_metrics.evaluate_compass` and `trainer_validation.family_k`. **Nothing on the test side named a database**, so no grep of `tests/` for `get_connection` could ever surface them, and a module-level import scan misses a function-local import too. Because the guard sits at path-resolution time inside `get_connection`, it fires on the production hop. **`trainer_validation.family_k` was NOT in A1's escape census — the guard found it.** It hid because its call sits behind a `_vm_up()` gate *and* because `family_k` floors at 1, so with live `bandit_posteriors` empty it returned the same value a scratch store returns: **correct by coincidence.**

The escape disappears without being fixed and returns the moment a file runs alone or ordering shifts. 🚨 **Do not install pytest here; if it is ever installed, these must be verified file-by-file first.**
